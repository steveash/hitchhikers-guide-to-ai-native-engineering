# Agentic Autofix Now Uses Copilot Memory

> GitHub's September 25, 2026 changelog announcing that agentic autofix now reads
> and writes Copilot Memory: it consults stored memories for context before fixing
> a security alert, stores the fix pattern it used as a new memory, and those
> memories are then available to other Copilot features (code review, cloud agent).
> The linked "About GitHub Copilot Memory" docs page (and its two management
> sub-pages) supply the architecture the changelog only gestures at: a two-tier
> repository-fact / user-preference memory model with citation-based validation,
> a 28-day unused-memory expiry, and a default-enablement policy that differs
> sharply between individual and enterprise/organization-managed plans.

## Source Context

- **Type**: docs (GitHub official product changelog, September 25, 2026; ~90-word
  body, "1 minute read"). Three linked documentation pages were also fetched and
  read in full, per MINER.md §1's instruction to follow substantive linked pages:
  "About GitHub Copilot Memory" (the changelog's own "Learn more" link), "Managing
  Copilot Memory for your personal account," and "Managing Copilot Memory for an
  organization or enterprise."
- **Author credibility**: GitHub engineering/docs team announcing and documenting a
  production feature integration in public preview. Authoritative for: the fact
  that agentic autofix now reads/writes Copilot Memory, the two-tier memory
  taxonomy, per-feature usage limits, retention/validation rules, and admin
  enablement/export/audit controls. Not a credible source for: measured impact on
  fix quality or speed from memory reuse, the underlying retrieval/ranking
  mechanism Copilot uses to select "relevant" memories, or real-world data on how
  often stored fix patterns are actually reused across alerts.
- **Scope**: Covers what agentic autofix's memory integration does, the general
  Copilot Memory architecture it plugs into (types, feature availability,
  retention, enablement, admin management), and audit/export controls for
  Business/Enterprise plans. Does NOT cover: fix acceptance-rate changes
  attributable to memory, memory retrieval latency or ranking, whether the 28-day
  retention clock is configurable, or any per-feature metrics specific to agentic
  autofix's memory usage (separate from the general Copilot Memory feature).

## Extracted Claims

### Claim 1: Agentic autofix now consults existing Copilot Memory entries for context before attempting to resolve a security alert, and stores the fix pattern it produces as a new memory

- **Evidence**: Opening paragraph of the changelog, stated as the core behavior
  change being announced.
- **Confidence**: settled (product fact, official changelog)
- **Quote**: "Agentic autofix now uses Copilot Memory for customers who've enabled
  it. When you use agentic autofix, it reviews existing memories for context that
  can help resolve security alerts. When it creates a fix, it stores the fix
  pattern as a memory for future use."
- **Our assessment**: This is a read-then-write loop layered onto the four-step
  explore→generate→validate→iterate→PR loop documented in
  `docs-github-copilot-agentic-autofix-code-scanning.md` (Claim 2): agentic autofix
  now begins each alert-remediation run by checking memory, and ends each
  successful run by writing to it. The changelog does not say *where* in the
  four-step loop memory consultation happens (e.g., during "explore relevant
  files" or as a separate pre-step), nor whether a memory miss changes behavior
  versus a memory hit — it states the input/output relationship, not the
  mechanism.

### Claim 2: Memories generated by agentic autofix can teach other Copilot features — specifically Copilot code review and Copilot cloud agent — about secure development patterns unique to a repository, in addition to helping agentic autofix resolve further alerts itself

- **Evidence**: Second paragraph of the changelog, naming the two other features
  by example.
- **Confidence**: settled (product fact, official changelog)
- **Quote**: "These memories can help agentic autofix resolve additional security
  alerts and teach other GitHub Copilot features (e.g., Copilot code review,
  Copilot cloud agent) about secure development patterns unique to your
  repository."
- **Our assessment**: This is the changelog's headline claim — cross-feature
  knowledge transfer through a shared memory layer, not feature-siloed learning.
  The "About GitHub Copilot Memory" docs page confirms and generalizes this same
  claim beyond security (Claim 6 below), and also states a feature-specific
  *limit* the changelog omits: Copilot code review only consumes repository-level
  facts, not user-level preferences (Claim 7). So "teach Copilot code review about
  secure development patterns" specifically means repository-level fact sharing,
  not sharing whatever a given developer's personal agentic-autofix session
  happened to prefer.

### Claim 3: Both agentic autofix and Copilot Memory are in public preview at the time of this announcement

- **Evidence**: Third paragraph of the changelog, a standalone status statement.
- **Confidence**: settled (product fact, official changelog)
- **Quote**: "Both agentic autofix and Copilot Memory are available in public
  preview."
- **Our assessment**: Both dependencies of this integration are themselves
  preview-stage features (agentic autofix per
  `docs-github-copilot-agentic-autofix-code-scanning.md`, July 2026; Copilot Memory
  per `docs-github-copilot-memory-user-preferences.md`, May 2026), so this
  integration compounds preview-stage instability on preview-stage instability —
  teams should expect the memory-assisted behavior described here to change before
  either underlying feature reaches GA.

### Claim 4: Copilot Memory stores two distinct memory types — repository-level facts (coding conventions, architectural decisions, build commands, project-specific rules; visible to all users with repo access) and user-level preferences (implied or stated personal interaction preferences; visible only to the originating user, or to an org/enterprise admin on Business/Enterprise plans)

- **Evidence**: "Types of memories" section of the linked "About GitHub Copilot
  Memory" docs page, presented as two named, bulleted categories with their
  visibility rules stated for each.
- **Confidence**: settled (product fact, official docs)
- **Quote**: "Repository-level facts — Facts about a repository, such as coding
  conventions, architectural decisions, build commands, and project-specific
  rules. Available to all users with access to Copilot Memory for that
  repository." / "User-level preferences — Implied or stated personal preferences
  about how a user wants to interact with Copilot. Available only to that user's
  Copilot interactions across repositories. For Copilot Business and Copilot
  Enterprise plans, they can be viewed and deleted by an organization or
  enterprise administrator."
- **Our assessment**: This is the general Copilot Memory taxonomy that the
  changelog's "existing memories" and "fix pattern as a memory" language (Claim 1)
  implicitly relies on without naming. For agentic autofix specifically: a "fix
  pattern" it stores is almost certainly a repository-level fact (it describes how
  *this repository's* code should be fixed, not a personal preference of the
  developer who triggered the run) — the docs page does not say this explicitly
  for agentic autofix, but it follows from the general definition and from the
  "unique to your repository" phrasing in the changelog's Claim 2 quote. This
  taxonomy directly corroborates and extends
  `docs-github-copilot-memory-user-preferences.md` Claim 1 (user-scope vs.
  repository-scope split) and its sibling `docs-github-copilot-memory-deletion-
  scope-cli.md` Claim 4 (scope-label transparency at capture time) — both prior
  notes described this same two-tier split without the "which specific features
  read which tier" detail this page adds (Claim 7 below).

### Claim 5: Copilot Memory is used by four features as of this writing — Copilot cloud agent, Copilot code review, Copilot CLI, and agentic autofix

- **Evidence**: Opening sentence of the "Feature availability" section, an
  explicit enumerated list.
- **Confidence**: settled (product fact, official docs)
- **Quote**: "Copilot Memory is currently used by Copilot cloud agent, Copilot
  code review, Copilot CLI, and agentic autofix."
- **Our assessment**: This confirms agentic autofix is the newest of four
  memory-consuming surfaces, not the first. The corpus previously documented
  Copilot CLI's `/memory on|off|show` commands
  (`docs-github-copilot-memory-deletion-scope-cli.md` Claim 3) but had no source
  explicitly stating Copilot code review or Copilot cloud agent also draw on the
  same memory store until this page. This turns memory from a per-feature add-on
  into a shared platform primitive spanning four distinct Copilot surfaces.

### Claim 6: Facts and preferences captured by one Copilot feature can be used by another — for example, a repository fact Copilot cloud agent discovers about database-connection handling can later inform Copilot code review's flagging of inconsistent patterns, and vice versa for cross-file settings synchronization

- **Evidence**: "Feature availability" section, giving two concrete worked
  examples of cross-feature reuse.
- **Confidence**: settled (product fact, official docs, illustrated with named
  examples)
- **Quote**: "Facts and preferences captured by one Copilot feature can be used by
  another. For example, if Copilot cloud agent discovers how your repository
  handles database connections, Copilot code review can later apply that
  knowledge to spot inconsistent patterns in a pull request. Similarly, if
  Copilot code review learns that certain settings must stay synchronized across
  two files, Copilot cloud agent will know to update both files when changing
  one."
- **Our assessment**: These two worked examples are the most concrete evidence in
  this source of what "shared memory across features" means operationally: a fact
  learned incidentally by one agentic surface changes a *different* surface's
  behavior on a later, unrelated task. This is a stronger and more general
  instance of the pattern in `blog-anthropic-claude-managed-agents-memory.md`
  Claim 11 (Wisedocs' cross-session memory identifying "common issues — including
  ones we didn't think about") — there, memory improved a single agent across its
  own sessions; here, memory improves a *different, independently-invoked*
  Copilot feature that never itself observed the originating interaction. This is
  new to the corpus: no prior note documents cross-*feature* (as opposed to
  cross-*session*) memory reuse in a commercial coding-agent product.

### Claim 7: Copilot CLI applies both repository-level facts and the initiating user's own user-level preferences; Copilot code review applies repository-level facts only and does not apply user-level preferences at all

- **Evidence**: "A few feature-specific limits apply" bullet list, immediately
  following the cross-feature examples in Claim 6.
- **Confidence**: settled (product fact, official docs)
- **Quote**: "Copilot CLI applies repository-level facts and the user-level
  preferences of the user who initiated the operation." / "Copilot code review
  uses repository-level facts only. User-level preferences are not applied during
  code review."
- **Our assessment**: This is a governance-relevant asymmetry the changelog itself
  never mentions: not every memory-consuming feature reads both tiers. For
  agentic autofix, this page does not state which tier(s) it reads or writes
  (a gap — see Extraction Notes), but the code-review exclusion is a useful
  precedent: GitHub appears to deliberately withhold personal/user-level
  preferences from surfaces that produce output visible to other reviewers (code
  review comments are seen by teammates), while allowing them in single-user
  surfaces (CLI sessions). If agentic autofix follows the same design logic, its
  PRs — which, like code review comments, are visible to the whole team — would
  plausibly draw only on repository-level facts, not the triggering user's
  personal preferences, though this is our inference, not a stated fact.

### Claim 8: Repository-level facts are stored with citations pointing to the code that supports them, and are only used after Copilot checks those citations against the current branch to confirm they're still accurate

- **Evidence**: "How Copilot Memory stores, retains, and uses information"
  section, "Repository-level facts" subsection.
- **Confidence**: settled (product fact, official docs)
- **Quote**: "Repository-level facts are stored with citations pointing to the
  code that supports them. When Copilot finds a fact relevant to its current
  work, it checks those citations against the current branch to confirm the
  information is still accurate. Only validated facts are used."
- **Our assessment**: This citation-and-revalidate mechanism is the concrete
  answer to a gap `docs-github-copilot-memory-user-preferences.md` (Extraction
  Notes) left open about how memory avoids becoming stale as code changes: rather
  than trusting a stored fact indefinitely, Copilot re-checks the fact's cited
  code against the *current* branch every time it's about to be used, and
  silently discards it if the citation no longer holds. For agentic autofix, this
  means a stored "fix pattern" that cites code since refactored or deleted would
  not be blindly reapplied — though the docs page does not confirm this
  citation-revalidation applies identically to agentic autofix's stored fix
  patterns versus other repository-fact sources; it is stated as a property of
  repository-level facts generally.

### Claim 9: User-level preferences are stored with citations that may include direct user quotes, and are revalidated at use-time via Copilot's "best judgment" rather than a citation check against code

- **Evidence**: Same section, "User-level preferences" subsection, drawing an
  explicit contrast with the repository-fact validation mechanism in Claim 8.
- **Confidence**: settled (product fact, official docs)
- **Quote**: "User-level preferences are stored with citations that may include
  direct user quotes. When Copilot finds a preference relevant to its current
  work, it uses its best judgment to confirm the preference still applies."
- **Our assessment**: The validation mechanism differs by memory type: repository
  facts get a mechanical citation-vs-current-branch check (Claim 8, an
  objectively checkable operation), while user preferences get a judgment call
  ("best judgment") with no stated mechanical check. This is a meaningfully weaker
  staleness guard for preferences than for facts — a preference inferred from one
  offhand remark could persist and be judged "still applicable" indefinitely with
  no code-level signal to contradict it, unlike a fact whose supporting code has
  since changed. Worth flagging for Ch06 governance guidance: repository facts
  have a built-in falsifiability check that user preferences lack.

### Claim 10: Any stored fact or preference that goes unused is automatically deleted after 28 days, and the 28-day timer resets whenever Copilot successfully validates and uses that entry

- **Evidence**: "Retention and validation" subsection, stated as an explicit
  numeric retention policy.
- **Confidence**: settled (product fact, official docs)
- **Quote**: "To prevent stale information from lingering, any stored fact or
  preference that goes unused is automatically deleted after 28 days. The 28-day
  timer may reset whenever Copilot successfully validates and uses an entry."
- **Our assessment**: This is a concrete, previously undocumented lifecycle detail
  that directly answers the "how long are patterns retained" question the
  Prospector's third triage comment flagged as missing from the changelog itself.
  The reset-on-use design means frequently-relevant memories persist indefinitely
  in practice (each successful use restarts the clock), while one-off or
  no-longer-applicable memories quietly expire within a month without requiring
  manual cleanup. For agentic autofix specifically, this implies a fix pattern
  used repeatedly across many alerts becomes effectively permanent, while a
  one-off fix pattern for an unusual alert type would silently disappear after 28
  days of disuse — a form of automatic institutional-knowledge pruning with no
  admin action required.

### Claim 11: Facts can also be captured from pull requests that were closed without being merged, but the citation-validation step (Claim 8) ensures such facts don't affect Copilot's behavior unless the current codebase still substantiates them

- **Evidence**: Final sentence of the "Retention and validation" subsection.
- **Confidence**: settled (product fact, official docs)
- **Quote**: "Facts can also be captured from pull requests that were closed
  without merging. In those cases, the validation step ensures that Copilot's
  behavior is unaffected unless the current codebase still substantiates the
  information."
- **Our assessment**: This is a safety detail for exactly the scenario agentic
  autofix creates by design — its output is always "a draft pull request ready
  for your review" (per `docs-github-copilot-agentic-autofix-code-scanning.md`
  Claim 2), meaning a meaningful fraction of its PRs may be closed unmerged if a
  reviewer rejects the fix. Without this safeguard, a rejected/incorrect fix
  pattern could still be memorized and silently reapplied to a future alert. The
  citation-revalidation mechanism (Claim 8) is what prevents that: a fact
  captured from an unmerged, rejected PR only survives to affect future runs if
  the code it cites is still present in the current branch — i.e., if the
  "fact" happens to also be independently true of the current codebase,
  regardless of whether that specific PR was accepted.

### Claim 12: Copilot Memory's default-enablement policy differs by plan tier: on by default for individual paid Copilot plans, but off by default for enterprise- and organization-managed subscriptions until an admin explicitly enables it — after which it becomes on-by-default for members, with individual opt-out

- **Evidence**: "Enabling Copilot Memory" section of the "About" page, corroborated
  and detailed further by the "Managing Copilot Memory for your personal account"
  and "Managing Copilot Memory for an organization or enterprise" sub-pages.
- **Confidence**: settled (product fact, official docs; consistent across three
  separate pages)
- **Quote**: "For individual plans, it's on by default. For enterprise- and
  organization-managed plans, an administrator must enable the policy first, and
  then individual users can opt out." (About page) / "For enterprise- and
  organization-managed Copilot subscriptions, Copilot Memory is off by default
  and must be enabled in the enterprise or organization settings. Once Copilot
  Memory is enabled, the feature is on for users by default. ... Individual
  users can opt out of Copilot Memory in their account settings." (admin
  management page)
- **Our assessment**: This is a meaningful update to, and partial supersession
  of, `docs-github-copilot-memory-user-preferences.md` Claim 6, which — based on
  the May 15, 2026 early-access changelog — inferred (at "emerging" confidence,
  explicitly not a direct quote) that "enabling user-level memory requires an
  explicit opt-in toggle ... it is not enabled by default." The current docs
  state plainly that individual paid-plan users now get Copilot Memory
  *on by default*, with no opt-in step. We read this as a **product-lifecycle
  progression rather than a live contradiction**: the May 15 source described an
  early-access, invitation/toggle-gated rollout to Pro/Pro+ users specifically;
  this September source describes the current, more mature state after the
  May 26 expansion to "public preview for all paid Copilot subscribers"
  (`docs-github-copilot-memory-deletion-scope-cli.md` Claim 5) — the same kind of
  early-access-to-broad-rollout progression that note already treated as
  non-contradictory. Per MINER.md §4a guidance not to file a contradiction issue
  when one side is weakly supported, we did not file one here: the superseded
  claim was itself graded "emerging"/inferred rather than a directly-quoted
  settled fact. We flag it here instead as a concrete update the Smith should
  apply: any existing guide text drawn from the older note's Ch05 recommendation
  to "add Copilot Memory activation to onboarding checklists" should be revised —
  for individual-plan users, no activation step exists anymore; the actionable
  guidance is now about the *enterprise/org opt-in gate and subsequent per-user
  opt-out*, not individual activation.

### Claim 13: If a user is assigned a Copilot subscription by more than one organization, the most restrictive Copilot Memory setting applies — the feature is not used for that user unless every one of those organizations has enabled it

- **Evidence**: A callout note in the "Enabling Copilot Memory" section of the
  admin-management page, addressing a specific multi-license edge case.
- **Confidence**: settled (product fact, official docs)
- **Quote**: "If a user is assigned a Copilot subscription by more than one
  organization, the most restrictive setting applies—that is, Copilot Memory
  will not be used unless all of those organizations have enabled this feature."
- **Our assessment**: This is a governance detail with no analogue in prior corpus
  notes on Copilot Memory: a single non-enabling organization can veto memory for
  a user even if all of that user's other organizations have opted in. Relevant
  for contractors or cross-org contributors — this is an AND-gate across
  organizations, not an OR-gate, and it is the more conservative (privacy-
  protective) design choice available.

### Claim 14: On Copilot Business and Enterprise plans, administrators can bulk-export or bulk-delete user-level preferences in JSONL format, for everyone or for individual users, with a two-hour export-result reuse window and a rate limit of 10 exports per hour

- **Evidence**: "Managing user-level preferences for an organization/enterprise"
  subsections of the admin-management page, describing the export/delete
  workflow and its stated limits.
- **Confidence**: settled (product fact, official docs)
- **Quote**: "You can export user-level preferences in JSONL format. You can do
  this for everyone at once or for individual users." / "Existing exports are
  reused for a two-hour window, so if someone else has requested a bulk export or
  an export for the same user within the last two hours, you may find the
  results are slightly out of date. Exports are limited to 10 per hour."
- **Our assessment**: This is the concrete administrative-governance surface that
  `docs-github-copilot-memory-user-preferences.md` (Extraction Notes) explicitly
  flagged as undocumented at the time: "how user-level memory interacts with
  repository-level memory" and management mechanics were unknown as of May 2026.
  This page resolves the *export/deletion* half of that gap directly: JSONL is a
  machine-readable, ingestible-elsewhere format, suggesting export is intended to
  support external compliance/audit tooling rather than just human inspection.
  The 10-exports/hour rate limit and 2-hour cache window are operational
  constraints an admin scripting bulk exports across a large organization would
  need to account for (e.g., pacing a full-org export across multiple calls, or
  accepting slightly-stale reused results for concurrent requests).

### Claim 15: Audit log events are generated when an administrator exports or deletes memories, and when a user opts out of Copilot Memory

- **Evidence**: "Auditing Copilot Memory" section of the admin-management page,
  a one-sentence summary of what triggers an audit event.
- **Confidence**: settled (product fact, official docs)
- **Quote**: "Events appear in your organization or enterprise's audit log when
  an administrator exports or deletes memories, and when a user opts out of
  Copilot Memory."
- **Our assessment**: This closes another gap the Prospector's third triage
  comment raised — "whether memory can be inspected/audited by humans before
  reuse ... critical for operational use in high-security contexts." The answer
  is partial: admin export/delete actions and user opt-outs are audited, but
  there is no stated audit event for the *creation* of a memory, nor for
  agentic autofix's own read-then-write memory operations described in Claim 1.
  An org's audit trail would show *that* an admin exported or deleted memories,
  and *that* a user opted out, but not a fine-grained log of which specific
  memories agentic autofix consulted or wrote on any given run.

```

(enterprise-cloud@latest/copilot/concepts/agents/copilot-memory)

REPOSITORY-LEVEL FACTS                | USER-LEVEL PREFERENCES
---------------------------------------|--------------------------------------
Coding conventions, architectural      | Implied or stated personal
decisions, build commands,             | preferences about how a user wants
project-specific rules                 | to interact with Copilot
Visible to: all users with repo access | Visible to: only the originating user
                                        | (+ org/enterprise admin on Biz/Ent)
Validated via: citation checked         | Validated via: Copilot's "best

Created by: users w/ write access +     | Created by: the specific user, from
Copilot Memory enabled                  | their own interactions
Deletable by: repository owner          | Deletable by: the user themself, or
                                        | an org/enterprise admin (Biz/Ent only)

FEATURE AVAILABILITY (as of Sept 25, 2026):
  Used by: Copilot cloud agent, Copilot code review, Copilot CLI,
           agentic autofix

PER-FEATURE READ LIMITS:
  Copilot CLI:         repo facts + initiating user's own preferences
  Copilot code review: repo facts ONLY (no user-level preferences)

  Unused fact/preference -> auto-deleted after 28 days
  Timer resets on each successful validate-and-use

ENABLEMENT DEFAULTS:
  Individual paid plan:            ON by default
  Enterprise/org-managed plan:     OFF by default until admin enables;
                                    then ON by default per user, with

  Multi-org edge case:             most restrictive org setting wins
                                    (AND-gate, not OR-gate)
```
