# Using DSPy to evaluate and improve Datasette Agent's SQL system prompts

> A reproducible experiment shows DSPy's GEPA optimizer rewriting Datasette
> Agent's actual production system prompt against its actual tool
> implementations: it fixed the one training failure its feedback showed it
> (+5 points train) but introduced a held-out regression (−10 points test)
> by adding advice that collided with the prompt's own `display`-mode
> semantics — and two of three apparent baseline failures turned out to be
> bugs in the eval metric itself, not the agent.

## Extracted Claims

### Claim 1: The DSPy harness evaluates and can rewrite datasette-agent's actual production system prompt while invoking its actual tool implementations against a real in-process Datasette instance, not a paraphrase or mock

- **Evidence**: The "Approach" section describes three fidelity measures: real
  tools (the DSPy agent calls `_sql_query`, `_describe_table`,
  `_list_databases_and_tables` — datasette-agent's actual implementations —
  against a real in-process `Datasette`, through the production
  `prepare_tool_output_for_model()` filter); real prompt (the static system
  prompt text is extracted at runtime from `_build_system_prompt()` and used
  as the DSPy signature's instructions, so "an optimized instruction string
  can be pasted straight back into `_build_system_prompt()`"); and faithful
  `display`-mode semantics (the metric scores the union of the final answer
  and any user-visible tables, so the token-saving `display='user'` mode
  isn't unfairly penalized).
- **Confidence**: emerging (first-party design description; verifiable because
  the harness code (`harness.py`) is published, but not independently
  re-run or audited by anyone outside this note's extraction)
- **Quote**: "The key idea is to make DSPy evaluate/optimize the *real* production artifacts rather than a paraphrase of them"
- **Our assessment**: This is the methodologically important design choice in
  the whole report. Most "eval a prompt" exercises test a copy or
  simplification of the prompt; here the harness pulls the literal string
  out of the running function and the literal tool code, so a passing score
  is evidence about the deployed system, not a proxy for it. This is the
  single biggest reason to treat the experiment's findings as applicable to
  the real datasette-agent rather than to a toy re-implementation.

### Claim 2: GEPA optimization fixed the one training failure its feedback identified (+5 points train) but introduced a held-out test regression (−10 points test) from a single accepted mutation, trained on only 20 questions

- **Evidence**: A before/after results table comparing the baseline
  production prompt to the GEPA-optimized prompt on train (20 q) and
  held-out test (10 q) splits, after the evaluation metric was corrected.
- **Confidence**: emerging (first-party, quantitative, from a single run of
  one optimizer configuration; no repeated trials or confidence intervals)
- **Quote**: "`dspy.GEPA` fixed the exact training failure its feedback showed it (+5 points train), but with only 20 training questions it also introduced one regression on the held-out set (−10 points test)"
- **Our assessment**: This is a clean, small-scale demonstration of
  optimizer overfitting on a tiny trainset — the exact failure mode named
  generically as "agents are famous cheaters" in
  `blog-langchain-better-harness-evals.md` Claim 6. Here it is not the agent
  cheating a visible eval but the *prompt optimizer* generalizing badly from
  20 examples, which is the harness-optimization analogue of the same risk.

### Claim 3: The regression was caused by GEPA-added advice colliding with the prompt's own `display`-mode semantics — the optimizer suggested checking distinct order statuses with `display='user'`, which hides result rows from the model, causing a held-out question to loop and fail

- **Evidence**: A worked failure trace: the optimized prompt added guidance
  to "query the distinct statuses first" with an example using
  `display='user'`; on a held-out question `gpt-4.1-nano` followed this
  literally, ran the query with `display='user'`, saw only `row_count: 3`
  (rows hidden by design), re-ran the identical query three times, exhausted
  its ReAct iteration budget, and answered with "here is the SQL I would
  run" instead of a number.
- **Confidence**: emerging (single traced failure, but the causal chain —
  prompt line → model behavior → iteration exhaustion — is documented
  step-by-step, not just asserted)
- **Quote**: "The optimizer's new advice interacted badly with the display-mode semantics defined elsewhere in the same prompt. Optimized prompts need regression review just like code — and this suggests a manual hardening of the production prompt: *\"never use `display='user'` for data you yourself need to read.\"*"
- **Our assessment**: This is the most instructive single finding in the
  source: a locally-plausible instruction (verify distinct values before
  filtering) becomes unsafe once it collides with a separately-defined
  mechanism (the `display` parameter's model-visibility contract) elsewhere
  in the same prompt. Automated prompt rewriting can introduce
  cross-instruction interactions a line-by-line human read might miss,
  which is a concrete argument for the "human review before production"
  gate that `blog-langchain-better-harness-evals.md` Claim 10 already
  recommends as a structural step, not an optional nicety.

### Claim 4: Two of three apparent baseline test failures were bugs in the evaluation metric rather than agent errors; correcting the metric raised the baseline test score from 81.7 to 95.0

- **Evidence**: Root-cause analysis of the first-pass test scores (baseline
  81.7, optimized 71.7): one failure was a "semantic zero" (gold answer `0`;
  the agent correctly said "no books have never been ordered," which
  contains no literal `0` for the checker to find), and one was an
  unhandled tie (a genuine 3-way tie for 3rd place where the gold checks
  only accepted one tiebreak order).
- **Confidence**: emerging (first-party root-cause analysis with the fix
  applied and the corrected score reported in the same report)
- **Quote**: "The first-pass test scores (baseline 81.7, optimized 71.7) overstated the drop because two shared failures were scorer artifacts, not agent errors"
- **Our assessment**: This is the headline methodological lesson of the
  report, stated explicitly by the author (see Claim 5), and it directly
  corroborates `blog-langchain-better-harness-evals.md` Claim 5 ("Quality >
  quantity ... a small set of well-tagged evals ... beats thousands of
  noisy but high-coverage evals") with a concrete before/after number: fixing
  two metric bugs in a 10-question test set moved the reported score by 13.3
  points — larger than the GEPA optimizer's own train/test delta.

### Claim 5: "Before optimizing a prompt against a metric, debug the metric against real transcripts" — stated as the report's explicit methodological takeaway

- **Evidence**: Direct statement following the metric-bug analysis in Claim 4,
  generalizing from the specific bookstore-dataset bugs to a rule for prompt
  optimization work in general.
- **Confidence**: emerging (a generalization stated once, from a single
  experiment, but consistent with standard ML practice of validating a
  metric before optimizing against it)
- **Quote**: "If GEPA had been run against the buggy metric *with these questions in its trainset*, it would have optimized toward the scorer's quirks. **Before optimizing a prompt against a metric, debug the metric against real transcripts.**"
- **Our assessment**: This is a sharper, more specific restatement of "at
  this scale, eval quality dominates optimizer quality" (the report's own
  TL;DR framing). The actionable instruction — read real transcripts before
  trusting the metric, not just before trusting the optimizer's output — is
  the most reusable single piece of guidance in the source for practitioners
  building their own DSPy or similar prompt-optimization harnesses.

### Claim 6: `gpt-4.1-mini` scored near ceiling on the baseline prompt (95.0 train / 96.7 test), leaving little headroom for a prompt optimizer, while `gpt-4.1-nano` had real headroom (90.0 train / 81.7 test) and was chosen as the optimization target to represent a "run the agent on a cheap model" scenario

- **Evidence**: A model-choice comparison table (both rows scored with the
  first-pass, pre-bugfix metric) followed by explicit reasoning for the
  model selection.
- **Confidence**: emerging (first-party, quantitative for two specific
  models on this one synthetic dataset; not a general claim about
  mini-vs-nano performance elsewhere)
- **Quote**: "gpt-4.1-mini is already near ceiling, so there is little for a prompt optimizer to do. gpt-4.1-nano has real headroom and represents a realistic \"run the agent on a cheap model\" scenario, so that's what I optimized for."
- **Our assessment**: This is a concrete, reusable heuristic for anyone
  setting up a prompt-optimization experiment: pick the model configuration
  that has room to improve, not the one that already performs best, or the
  optimizer will have nothing to learn from (as happened later with GEPA's
  plateau — see Claim 7).

### Claim 7: GEPA rewrote the ~2,400-character production prompt into an ~8,800-character rulebook in a single accepted mutation, then plateaued because nearly every training minibatch already scored 100%

- **Evidence**: Direct size comparison of `baseline_prompt.txt` (2,331 bytes,
  confirmed by direct fetch) and `optimized_prompt.txt` (8,825 bytes,
  confirmed by direct fetch), with the optimizer's subsequent behavior
  described.
- **Confidence**: emerging (first-party; sizes independently verified by
  fetching both files directly for this note)
- **Quote**: "GEPA accepted one mutation: it rewrote the ~2,400-char production system prompt into an ~8,800-char rulebook (see `baseline_prompt.txt` vs `optimized_prompt.txt`). After that it plateaued — nearly every training minibatch already scored 100%, so reflection had nothing to work with."
- **Our assessment**: A roughly 3.7x size increase in one mutation, with no
  further mutations accepted, suggests GEPA converged very quickly on this
  small trainset rather than iteratively refining — consistent with Claim 6's
  concern about the trainset being too easy (20 questions, 90% baseline) to
  drive multiple rounds of reflection. This is a caution against reading "the
  optimizer converged" as "the optimizer found the best prompt" when the
  training signal saturates this fast.

### Claim 8: A schema-listing design flaw — showing only table names plus an instruction not to call `describe_table` if information is "already available" — caused the model to guess column names and enter error-retry loops in baseline traces

- **Evidence**: Named directly by Willison in the beat post as the finding he
  found most interesting, and repeated in the README's "Takeaways" section
  with the same wording.
- **Confidence**: emerging (first-party trace analysis; the specific guessed
  column names are given as concrete examples, indicating this was observed
  in actual baseline traces, not inferred)
- **Quote**: "The schema listing gives only table names; the \"don't call describe_table if you already have the information\" advice caused column-name guessing (page_count, o.order_id, first_name) and error-retry loops in baseline traces. Either include column names in the prompt's schema listing or soften that advice."
- **Our assessment**: This is a specific, actionable prompt-design bug: an
  instruction meant to save tool calls (don't re-fetch schema you already
  have) backfires when the schema summary the model "already has" is
  incomplete (table names only, no columns), forcing the model to guess
  rather than ask. The general pattern — a token-saving shortcut instruction
  interacting badly with an incomplete context artifact — is likely to recur
  in other SQL/tool-calling agents that summarize schema to save tokens.

### Claim 9: A remaining known failure was not fixed by GEPA: both baseline and optimized prompts answer "which customer spent the most" with a raw customer ID rather than joining to look up the name, because the failure only appears in the held-out split and GEPA cannot learn from examples it never sees

- **Evidence**: A specific failure example (both programs answering
  "customer ID 16 ($943.82)" instead of a name, scoring 0.5) with the
  proposed fix and an explanation of why the optimizer missed it.
- **Confidence**: emerging (first-party; single documented failure instance,
  but the trainset/holdout mechanism explanation is a direct, verifiable
  property of the experiment's own design, not speculation)
- **Quote**: "Both programs answer \"Which customer spent the most…\" with \"customer ID 16 ($943.82)\" — never joining to `customers` for the name (score 0.5). The fix is a prompt rule like \"prefer human-readable identifiers: join to look up names for IDs you report.\" GEPA couldn't discover it because the failure only occurs in the held-out split — trainset coverage bounds what the optimizer can learn."
- **Our assessment**: This is a precise, falsifiable statement of a general
  limitation of trainset-driven prompt optimization: the optimizer is
  structurally blind to failure modes absent from its training distribution,
  regardless of optimizer quality. It reinforces Claim 6's "pick a model
  with headroom" advice with a corollary — pick (or grow) a trainset with
  *coverage* of the failure modes you want fixed, not just headroom on
  aggregate score.

- **Evidence**: The beat post frames the whole project as an asynchronous

### Claim 11: The harness's optimized-instruction output is designed to paste directly back into datasette-agent's production prompt-building function, making the DSPy setup a reusable regression-test suite for prompt changes, not just a one-shot optimizer run

- **Evidence**: Stated as a design property of the harness (the extracted

  optimized string round-trips back into the same function) and restated as
  the first of three "Takeaways for datasette-agent."
- **Confidence**: emerging (first-party design claim; plausible given the

- **Our assessment**: This reframes the harness's value beyond the single

### Baseline production system prompt (verbatim, extracted at runtime from `_build_system_prompt()`)

```
You are a helpful data analysis assistant. You have access to tools that let you explore and query databases. Use the tools to answer questions about the data. The available databases and tables are listed below - do not call list_databases_and_tables or describe_table if you already have the information you need from this prompt or the conversation history. Only describe a table when you need column details you haven't seen yet.

When calling a tool, pass the arguments directly as a flat JSON object matching the tool's parameters. Always explicitly specify the 'database' parameter for any database tools (e.g., sql_query, describe_table) based on the available databases listed below. For sql_query, provide your SQL in the 'sql' parameter. Do NOT wrap tool arguments inside a 'kwargs' key (e.g., do not use {"kwargs": {"param": "value"}}).

Your output will be rendered as markdown. Escape underscores in identifiers like column names and table names with a backslash (e.g. table\_name, row\_count) to prevent them from being interpreted as italic markers. This is not necessary inside backtick code spans like `table_name`.

When you call sql_query, pick a `display` mode for the result:
- `model` (default): rows come back to you only. Pick this when you need to reason over the numbers but won't be quoting them back to the user verbatim (e.g. counting rows before a join, checking a value to decide what to query next).
- `both`: rows come back to you AND a rendered table is shown to the user. Pick this whenever your answer will reference specific data — the user gets the table inline, you get to comment on it.
- `user`: a rendered table is shown to the user; you only see column names and row_count, not the rows themselves. Pick this for "show me…", "list the…", or "what are the top…" requests where the user wants to read the data and you don't need to summarize the contents. This saves tokens on bulk fetches.

When you use `both` or `user`, the rendered table IS your answer for that data — do NOT then repeat the same rows as a markdown table or bullet list in your text. The user already sees the table inline. Your text response should add value the table doesn't: a one-line takeaway, a caveat, a follow-up suggestion, or just a brief framing sentence. If there's nothing to add, say nothing.
```
*Source: `baseline_prompt.txt`, github.com/simonw/research/tree/main/dspy-datasette-agent-prompts, fetched directly, 2331 bytes.*

### GEPA-optimized prompt (verbatim, `optimized_prompt.txt`) — includes the line that caused the held-out regression (Claim 3)

```
You are an Agent-style data-analysis assistant that uses the provided tools to explore databases and answer user questions. Follow these rules exactly when planning and making tool calls. This instruction supplements any per-episode `schema_hint` or `question` you receive.

General interaction & output format
- In each agent turn you must interleave:
  - next_thought: your internal reasoning and plan for the next step(s).
  - next_tool_name: the tool you will call next (one of list_databases_and_tables, describe_table, sql_query, finish).
  - next_tool_args: the tool arguments as a flat JSON object (no "kwargs" wrapper). The JSON must be valid.
- After each tool call you will receive an observation. That observation becomes part of the trajectory you can use for subsequent steps.
- When you decide the task is complete, call the finish tool (next_tool_name = finish with next_tool_args = {}).
- Your final user-facing answer will be produced after finish; ensure you have collected all needed data before calling finish.

[... tool-calling and formatting rules omitted for length; full text at
github.com/simonw/research/tree/main/dspy-datasette-agent-prompts/optimized_prompt.txt ...]

SQL guidance & common pitfalls (domain-specific guidance)
- Always verify the table structure (columns and column names) when you need to reference specific columns. Use describe_table only when necessary.
- Prefer transactional/priced values from order-related tables when calculating revenue:
  - If an order_items (or equivalent) table has a unit_price (the price at sale time) and quantity, prefer SUM(quantity * unit_price) over SUM(quantity * product_list_price) because product list prices can differ from sale prices.
  - Use COALESCE where necessary: e.g., COALESCE(oi.unit_price, b.price, 0) to avoid NULLs affecting SUMs.
- To filter by year in textual date columns, use functions appropriate to SQLite-like / typical DBs in examples (e.g., strftime('%Y', order_date) = '2023') — but first confirm the column type in describe_table.
- When counting customers/orders, be explicit:
  - Unique customers: COUNT(DISTINCT customer_id)
  - Percentage calculations: CAST(numerator AS REAL) / NULLIF(denominator, 0) * 100 and ROUND(..., 1) for one decimal place.
- When handling statuses (e.g., excluding or including cancelled orders), carefully parse the user's request; if unsure, query the distinct statuses first (e.g., SELECT DISTINCT status FROM orders) and confirm the values before filtering.
- For monetary outputs, round to two decimal places when appropriate (e.g., ROUND(SUM(...), 2)) unless the user requests another format.
- Double-check JOIN logic and join keys. If foreign keys were listed in describe_table, prefer those columns to build correct joins.
- When aggregating across multiple tables, always join on the correct id columns and consider order-level filters (status, date) at the right stage of the query.

[...]

Examples of good SQL patterns (you may adapt to actual column names discovered via describe_table):
- Count distinct customers in 2023:
  {"database":"books","sql":"SELECT COUNT(DISTINCT customer_id) AS cnt FROM orders WHERE strftime('%Y', order_date) = '2023'","display":"model"}
- Total revenue from a genre (use order_items.unit_price when present):
  {"database":"books","sql":"SELECT ROUND(SUM(oi.quantity * COALESCE(oi.unit_price, b.price)), 2) AS total_revenue FROM order_items oi JOIN books b ON b.id = oi.book_id WHERE b.genre = 'Mystery'","display":"model"}
- Percentage of delivered orders:
  {"database":"books","sql":"SELECT ROUND(100.0 * SUM(CASE WHEN status = 'delivered' THEN 1 ELSE 0 END) / NULLIF(COUNT(*),0), 1) AS pct_delivered FROM orders","display":"model"}
- Show distinct order statuses before filtering:
  {"database":"books","sql":"SELECT DISTINCT status FROM orders","display":"user"}
```
*Source: `optimized_prompt.txt`, github.com/simonw/research/tree/main/dspy-datasette-agent-prompts, fetched directly, 8825 bytes.
