# Software factories and code reviews with Harjot Gill

> A vendor CEO's first-person account of running an agent-heavy "software factory": release-level (not PR-level) review, a strike-based review-exemption list, layered agent verification (TLA+, simulation, API emulation, staged rollouts), and extreme AI spend.

## Source Context

- **Type**: blog-post (podcast episode page; Orosz's written takeaways, the transcript is not in the static page text)
- **Author credibility**: Orosz is an experienced engineering writer who interviews and adds commentary. Harjot Gill is founder/CEO of CodeRabbit, which **sells AI code review**, so he has a commercial interest in "human review is dead" and in high AI spend. Orosz notes CodeRabbit is an outlier.
- **Scope**: Covers CodeRabbit's internal practice (about 40 engineers), verification layers, review governance, spend, hiring. Does not give methodology or data for the quality claims. All numbers are self-reported by the interviewee.

## Extracted Claims

### Claim 1: Engineers at CodeRabbit review releases (batches of PRs) and plans rather than individual agent-generated PRs
- **Evidence**: Interviewee's description of internal practice; no metrics on defect rates.
- **Confidence**: anecdotal
- **Quote**: "Harjot thinks that we will stop reviewing code generated by agents. Instead, we’ll spend more time reviewing the planning and final asset. Inside of CodeRabbit, engineers are reviewing releases (multiple PRs), not individual PRs."
- **Our assessment**: Specific, checkable mechanism (review unit = release) but single-source and from a vendor that sells review. Useful as a concrete variant of "review the plan" patterns; no outcome data.

### Claim 2: A "review exempt list" lets trusted devs push to production unreviewed, with a strike system that revokes exemption after production breakages
- **Evidence**: Interviewee's description; Orosz endorses it. No numbers on strike thresholds.
- **Confidence**: anecdotal
- **Quote**: "The company has a “review exempt list” of devs who can push to production without anyone reviewing their releases. When an outage happens, the team traces the PR that broke prod, and the dev who pushed it gets a ‘strike.’ Rack up enough strikes and releases have to be reviewed by colleagues."
- **Our assessment**: Novel governance mechanism: trust that is earned and revocable, tied to post-incident attribution. Threshold, trace method and blame culture implications are unspecified. Worth including as an example, flagged as untested elsewhere.

### Claim 3: Agents need to "hill climb": a layered stack of verification the agent can run itself
- **Evidence**: Interviewee lists layers used by his team (formal models, local simulation, API emulation, dev environments, staged production rollouts).
- **Confidence**: anecdotal
- **Quote**: "Harjot believes agents need to be “hill climbing”; they need to have ways to verify their own work"
- **Our assessment**: A good organizing frame consistent with the corpus's verification emphasis; the layers are named but not detailed.

### Claim 4: TLA+ found race conditions on a CodeRabbit product that code review overlooked
- **Evidence**: Single anecdote, no specifics (which product, how many bugs).
- **Confidence**: anecdotal
- **Quote**: "For one of their products, the engineering team utilized TLA+, and found race conditions that the code review overlooked."
- **Our assessment**: Plausible and consistent with the TLA+ literature, but unquantified. Lean is only "experimenting".

### Claim 5: Local deterministic simulation and real-API emulation are part of the verification stack
- **Evidence**: Interviewee says they built a simulation harness and mock Google Cloud APIs.
- **Confidence**: anecdotal
- **Quote**: "One of the infra pieces built at Harjot’s startup is a simulation harness to fuzz different interleavings (concurrent operations)."
- **Our assessment**: Corroborates deterministic-simulation advocacy; no detail on how determinism is achieved.

### Claim 6: Staged rollouts with feature flags, with an agent watching rollout metrics/logs and widening when stable
- **Evidence**: Interviewee's description; Orosz links it to OpenAI's Perf Factory.
- **Confidence**: anecdotal
- **Quote**: "He said they often have an agent observe the performance characteristics of the rollout, check the logs, and continue the wider rollout when things are stable."
- **Our assessment**: Shifts the final verification gate from pre-merge review to production observation. "often" signals inconsistent use.

### Claim 7: Fine-tuning review models stopped being worthwhile because frontier models move too fast
- **Evidence**: Interviewee's statement, from a company that previously did fine-tune.
- **Confidence**: anecdotal
- **Quote**: "CodeRabbit used to invest in fine-tuning models used in AI review, but Harjot says that new frontier models moving faster means that it would be tough to maintain their own fine-tuned ones, so it’s not worth it."
- **Our assessment**: Credible first-hand reversal; a maintenance-cost argument rather than a quality benchmark.

### Claim 8: ~5,000 PRs/month at ~$150/PR and ~$250-275K/month personal AI spend, with a 40-engineer team
- **Evidence**: Self-reported; Orosz contrasts with typical $200-$2,000/month per dev. Much of the PR volume is "janitorial" (CI fixes, flaky tests, caching).
- **Confidence**: anecdotal
- **Quote**: "Harjot estimates that a PR costs him around $150 in a personal spend of around $250-$275K per month."
- **Our assessment**: Unverified, single vendor outlier; PR count is a weak productivity measure (see existing ROI note). Do not use as benchmark.

### Claim 9: Massive spend is justified only where AI output becomes commercial R&D; Orosz says it is not typical
- **Evidence**: Orosz's analysis.
- **Confidence**: anecdotal
- **Quote**: "It’s not the same at places with fixed customer bases willing to pay a certain amount for an existing product, and no more."
- **Our assessment**: A useful conditioning variable on spend advice, not a contradiction of spend-cap guidance.

### Claim 10: CodeRabbit rebuilt its CI in-house with agents in about a week after a $13M/year quote
- **Evidence**: Interviewee anecdote relayed by Orosz.
- **Confidence**: anecdotal
- **Quote**: "It took a week, and the new CI cost 50% less than the quote, with similar performance."
- **Our assessment**: Interesting build-vs-buy datapoint; no independent verification, and a separate post mentions CI capacity stalls.

### Claim 11: "War rooms" where engineers, product and design steer agents together to produce a prototype then product
- **Evidence**: Interviewee's description; Orosz compares to Uber 2016.
- **Confidence**: anecdotal
- **Quote**: "To get important stuff done, engineers, product folks, and designers gather in the room and steer the agents as together they build a prototype, then a working product."
- **Our assessment**: A team-organization pattern; thin detail.

### Claim 12: Agents ran long, large tasks (six-week WAL in Rust; Bun migration over a weekend)
- **Evidence**: Interviewee examples, WAL "now in production".
- **Confidence**: anecdotal
- **Quote**: "A write-ahead log (WAL) on top of object stores using Rust (the agent ran for six weeks!). This WAL is now in production."
- **Our assessment**: Data point for long-running agents; no detail on harness or oversight.

## Concrete Artifacts

```
Verification layers listed by Gill (source: takeaway 5):
1. Formal models (TLA+, experimenting with Lean)
2. Local deterministic simulations (fuzz interleavings)
3. Emulating real APIs (e.g. Google Cloud APIs)
4. Dev environments (agents deploy to Google Cloud / Vercel and confirm they work)
5. Production: feature flags + progressive rollout, agent observes metrics/logs
```

```
Review governance (source: takeaways 6-7):
- Unit of review = release (multiple PRs); plan and final asset reviewed
- "review exempt list" -> may push to prod unreviewed
- outage -> trace breaking PR -> dev gets a strike -> enough strikes -> releases need colleague review
```
