# condense-json 1.0

> A short release-announcement post for `condense-json` 1.0, a Python
> library that de-duplicates JSON by replacing repeated strings/subtrees
> with compact `{"$": id}` references — followed within the same day, in a
> linked `llm` PR, by a concrete practitioner deployment that restores raw
> LLM provider-response storage while measuring 42-86% size reduction on
> live payloads, which in turn drove a same-day 1.0-to-1.1 feature addition
> (structural and merge-patch replacements) back into the library itself.

## Extracted Claims

### Claim 1: `condense_json` compresses JSON by replacing strings that match entries in a caller-supplied `replacements` mapping with compact `{"$r": [...]}` or `{"$": id}` reference markers, and `uncondense_json` reverses the transform
- **Evidence**: The blog post's own worked example (a nested JSON object
  with the substring "with foxes in it" appearing twice, condensed against
  a one-entry replacements object into `{"$r": [...]}` markers), plus the
  matching example in the library README.
- **Confidence**: settled (directly demonstrated with input/output
  examples in both the blog post and the README)
- **Quote**: "It scans for strings or substrings that are present in that
  replacements object and replaces those with a special `{"$r": ...}`
  syntax in the output."
- **Our assessment**: This is a straightforward, verifiable mechanism —
  substring-level deduplication against a caller-provided dictionary,
  rather than generic compression (gzip/zstd). The caller decides what
  counts as "known duplicate data," which is why it composes well with a
  database schema where the duplicate content already lives in another
  table (see Claim 6).

### Claim 2: The library's stated motivation is avoiding storage of duplicated data across related JSON structures, and it was originally built for this purpose in `llm`'s SQLite logs
- **Evidence**: The author's own one-sentence statement of intent in the
  blog post.
- **Confidence**: settled (first-party statement of original design intent)
- **Quote**: "The idea is to make it easier to store JSON that includes
  duplicated data from other related structures. I use it to save space in
  the SQLite logs generated by LLM"
- **Our assessment**: This frames the whole library as a solution to a
  specific storage-engineering problem — a JSON payload that partially
  overlaps with data already persisted elsewhere — rather than a
  general-purpose compression tool. That framing matters for Guide
  Impact: the technique is not "compress your JSON," it is "stop storing
  the same string twice across two tables."

### Claim 3: condense-json 1.0 adds escaping of `$`, `$r`, and `$raw` marker keys so that condensing/uncondensing round-trips are lossless even when the input JSON legitimately contains dictionaries shaped like the library's own reference markers
- **Evidence**: GitHub 1.0 release notes (`github.com/simonw/condense-json/releases/tag/1.0`), corroborated by the README's dedicated "Escaping of `$`, `$r` and `$raw` keys" section with a worked example (`{"price": {"$": "100"}}` round-trips via a `{"$raw": ...}` wrapper).
- **Confidence**: settled (documented release note plus a runnable
  round-trip example in the README)
- **Quote**: "`condense_json()` now can now round-trip inputs that include
  the keys `$`, `$r`, and `$raw`. These are now escaped using a `$raw`
  wrapper."
- **Our assessment**: This is the headline correctness fix of the 1.0
  release (the version bump itself signals it as the primary breaking/
  stabilizing change). Without it, a payload that happens to contain a
  dict shaped like `{"$": "100"}` for unrelated reasons (e.g., a JSON
  value literally named `$`) would be misinterpreted as a condense-json
  marker on the way back out — a correctness bug specifically in the
  "safe on arbitrary/untrusted-shape payloads" sense that the `llm`
  integration (Claim 6) explicitly relies on.

### Claim 4: condense-json 1.0 makes overlapping-replacement resolution deterministic by always preferring the longest match, scanned left to right, regardless of the replacements dictionary's iteration order
- **Evidence**: GitHub 1.0 release notes.
- **Confidence**: settled (documented release note, corroborated by the
  README's "longest match wins" rule statement)
- **Quote**: "Overlapping replacements are now deterministic: matches are
  selected from left to right, with the longest match winning."
- **Our assessment**: Determinism under overlap resolution matters for any
  system that diffs or hashes condensed output (e.g., for caching or
  content-addressing condensed records) — a non-deterministic condenser
  would produce different byte output for logically identical input
  depending on internal dict ordering, breaking any downstream assumption
  of stable serialization.

### Claim 5: condense-json 1.0 makes `uncondense_json` fail loudly on malformed condensed input via a typed `UncondenseError` (a `ValueError` subclass) instead of silently producing corrupted output
- **Evidence**: GitHub 1.0 release notes, corroborated by the README's
  description of `UncondenseError`'s specific trigger conditions (unknown
  replacement IDs, non-list `$r` values, invalid `$r` segments, malformed
  merge references) and a runnable example catching it.
- **Confidence**: settled (documented release note plus README example)
- **Quote**: "`uncondense_json()` now raises `UncondenseError`, a subclass
  of `ValueError`, for malformed condensed data, including unknown or
  blank replacement IDs, non-list `$r` values, and invalid `$r` segments."
- **Our assessment**: This "fail loudly, not silently" design choice is
  precisely what the downstream `llm` integration depends on for
  correctness reporting — see Claim 7, where a payload whose references no
  longer resolve is deliberately surfaced via this same typed error rather
  than returned as silently-wrong data.

### Claim 6: A real deployment (GitHub PR simonw/llm#1586, merged 2026-08-03) uses condense-json to restore full raw-provider-payload logging in the `llm` tool's SQLite store without re-storing content the database already holds elsewhere
- **Evidence**: The PR's own description of what it does — a new nullable
  `turns.response_json` column stores the full provider payload, with
  strings of 64+ characters that already appear in the turn's own messages
  (response text, reasoning summaries, tool arguments/output, provider
  metadata) replaced by position-keyed references (e.g.
  `{"$": "0.0.text"}`) instead of being duplicated.
- **Confidence**: settled (first-party PR description and merged code, by
  the same author as the library)
- **Quote**: "Restores per-call storage of the raw provider payload, which
  was dropped entirely when logging moved to the message store. The
  payload lands in a new nullable `turns.response_json` column, condensed
  with `condense-json` so nothing the parts tables already hold is stored
  twice."
- **Our assessment**: This is a concrete, load-bearing production use of
  the library's stated purpose (Claim 2): a database schema where a raw
  API payload overlaps heavily with data already normalized into other
  tables, and condense-json is the mechanism used to store the payload
  "for free" (mostly references) rather than paying for full duplication.
  This is directly relevant to Ch04 (Context Engineering) as a concrete
  storage-layer pattern for any harness or logging system that persists
  both structured conversation state and raw provider responses.

### Claim 7: The replacement dictionary itself is never stored on disk — it is reconstructed at read time from the message chain, and any reference that fails to resolve raises a typed error rather than returning corrupted data
- **Evidence**: The PR's description of the read path.
- **Confidence**: settled (first-party PR description of implemented and
  merged behavior)
- **Quote**: "the replacement dict is never stored; it is rebuilt from the
  chain segment between the turn's parent and tip, which is sound because
  message content is hash-frozen."
- **Quote (error handling)**: "A payload whose references no longer resolve
  is absent from listings but raises `UncondenseError` from the API."
- **Our assessment**: This is the specific engineering move that makes the
  storage saving "real" rather than illusory — the replacements mapping
  itself would otherwise need to be stored per-record (or be a fixed
  global table), which could reintroduce the duplication the whole scheme
  is meant to avoid. Reconstructing it on the fly from data that is
  already guaranteed immutable ("hash-frozen") avoids that trap, at the
  cost of coupling correct decoding to the message chain still being
  intact.

### Claim 8: Measured on live calls, condensing the raw provider payload before storage cut a 400-word gpt-4o-mini response from 3,288 bytes to 473 bytes (86% reduction), with short answers seeing 42-48% reduction
- **Evidence**: The PR author's own measurement, stated in the PR
  description.
- **Confidence**: emerging (a first-party, single-author measurement on
  live calls against two response-length categories; not an independently
  reproduced benchmark, no sample size given beyond "a 400-word" example
  and unspecified "short answers")
- **Quote**: "Measured on live calls: a 400-word gpt-4o-mini answer
  condenses 3,288 B → 473 B (86%); short answers run 42–48%."
- **Our assessment**: An 86% reduction on a longer response is a strong
  headline number, but note the compression ratio is response-length
  dependent (42-48% on short answers) because what's being eliminated is
  the *provider envelope* (ids, usage, fingerprints, logprobs, settings
  echoes — see Claim 9) — a roughly fixed-size overhead — relative to the
  response body, which is the variable-size part. This is a token/storage
  efficiency data point, but its magnitude should be quoted with that
  length-dependence attached, not as a flat "condense-json saves ~85%."

### Claim 9: What remains in the condensed payload after storage is essentially the provider envelope — ids, usage breakdowns, fingerprints, logprobs, and settings echoes — that had no other equivalent in the existing schema
- **Evidence**: The PR's own description of the payload's residual content
  after condensing, and the stated motivation for restoring the column at
  all ("everything with no part equivalent: usage breakdowns, fingerprints,
  logprobs, settings echoes").
- **Confidence**: settled (first-party PR description of implemented,
  merged behavior)
- **Quote**: "What remains in the column is roughly the provider envelope —
  ids, usage, fingerprints, logprobs, settings echoes — which is precisely
  the data that had been lost."
- **Our assessment**: This is a useful general lesson independent of
  condense-json specifically: when a team decides to stop logging "the
  whole raw response" for storage-efficiency reasons (as `llm` had
  previously done — see Claim 2 / Extraction Notes), the concrete cost is
  losing exactly this class of provider-metadata fields, which have no
  equivalent anywhere else in a normalized conversation schema. Any guide
  advice on "should we log full raw API responses" should name this
  specific field class as what's actually at stake.

### Claim 10: In the same integration, echoed tool definitions in the response payload accounted for 40% of a real tool-using turn's stored size before condensing was extended to cover them; after extending it, a live gpt-5-mini tool call went from 4,784 bytes raw to 1,856 bytes stored
- **Evidence**: A follow-up commit in the same PR, described by the author,
  that adds the turn's own tool `(name, description)` pairs to the
  replacements mapping so provider-echoed tool descriptions (which
  providers return in full on every response) match against the tools
  table's own copy instead of being stored a second time.
- **Confidence**: emerging (first-party measurement of a single live tool
  call; the "40%" figure is stated as an observed proportion on "a real
  tool-using turn," not a formal benchmark)
- **Quote**: "Providers echo the full tool definitions back in every
  response payload. On a real tool-using turn that echo was 40% of the
  stored payload, led by long tool descriptions - strings the tools table
  already holds, linked to the turn via turn_tools."
- **Quote (measured result)**: "Measured live on a gpt-5-mini tool call:
  4,784 B raw -> 1,856 B stored."
- **Our assessment**: This is a distinct, second instance of the general
  pattern in Claim 2/6: any API response field that echoes back
  caller-supplied data (tool definitions, in this case) is a candidate for
  condense-json-style deduplication against the table that already holds
  the canonical copy. The author explicitly declined to extend this to
  parameter *schemas* specifically because providers transform the schema
  on the way back (e.g., OpenAI strict mode injects `additionalProperties`
  and `strict` keys), so the echoed form would not byte-match the stored
  original — a concrete limit on where this technique applies (it needs
  exact-string recurrence, not semantic equivalence).

### Claim 11: A same-day debugging discovery — that streamed reasoning content was stored as two different ciphertexts of the same underlying text because the provider encrypts per-event — was fixed by re-emitting the final payload's reasoning metadata after the stream ends, which raised measured condensation savings on that path from 15% to ~50%
- **Evidence**: The PR author's own description of the bug and fix, plus
  the before/after compression measurement on streamed gpt-5-mini calls
  (sync and async, explicitly verified live).
- **Confidence**: settled for the mechanism (first-party description of a
  diagnosed and fixed bug in merged code) / emerging for the specific 15%
  to 50% figure (single-author live measurement, not an independent
  benchmark)
- **Quote**: "Streamed Responses API calls stored different ciphertexts of
  the same reasoning in the part metadata (harvested at
  `response.output_item.done`) and in `response_json` (from
  `response.completed`) — OpenAI encrypts per event. The plugin now
  re-emits reasoning `provider_metadata` from the final payload after the
  stream ends, so both records agree on one blob. Verified live on
  streamed gpt-5-mini, sync and async: condensation savings go from 15% to
  ~50%."
- **Our assessment**: This is a subtle but instructive failure mode for
  anyone deduplicating against provider responses that involve per-event
  encryption or per-event nondeterminism: byte-for-byte string matching
  (which is what condense-json relies on — see Claim 1's "Matching is
  strictly structural" / substring rules) silently stops working if the
  two copies of "the same" content are not byte-identical, even though
  they are semantically identical. The fix here isn't in condense-json
  itself — it's upstream, making the two records agree on the exact same
  ciphertext before condensing ever runs. Worth flagging as a general
  caveat: exact-match deduplication schemes require their inputs to
  actually be exact matches, which streaming/per-event provider behavior
  can silently violate.

### Claim 12: The `llm` integration work directly motivated same-day extensions to condense-json itself — structural replacements (whole dict/list subtree matching) and merge references (a base object plus a small patch) — which shipped as condense-json 1.1 roughly 6.5 hours after the 1.0 release this post announces
- **Evidence**: The PR author's own comment mid-PR, linking to
  `simonw/condense-json#8` ("Structural and merge replacements, Hypothesis
  property tests," merged), and independently confirmed via the
  condense-json GitHub releases list: 1.0 released 2026-08-02 22:19 UTC,
  1.1 released 2026-08-03 04:56 UTC.
- **Confidence**: settled (directly observable release timestamps plus
  first-party statement connecting the two)
- **Quote**: "This turned into an exploration of what it would be like if
  condense-json could handle replacements where the values were more
  complex objects than strings. That helped. But then I noticed that the
  wrapper object - especially for OpenAI - had a whole bunch of common
  key/values like "top_logprobs": 0 and "truncation": disabled so I
  started playing with the idea of more complex merge operations - the
  replacements array specifies a big object, then in the condensed form we
  say "take that object and replace these keys". And THAT looks very
  promising. So I'm probably going to do a condense-json 1.1."
- **Our assessment**: This is a clean, dated example of dogfooding driving
  a library's design in near-real time: applying a general-purpose tool to
  a specific real payload (OpenAI's verbose response envelope, which
  repeats large blocks of near-identical settings/metadata across calls)
  surfaced a gap (string-only matching couldn't dedupe whole near-identical
  *objects*, only substrings) that was closed within hours, in the same
  work session, by the same author who maintains both projects. Note that
  this note's Claim 1 example and the "1.0" framing of this blog post
  describe only the string/substring-matching mechanism; structural and
  merge-reference matching (documented in the current README, quoted where
  needed elsewhere in this note) is 1.1-and-later behavior, not part of
  the 1.0 release the post announces. See Extraction Notes for how this
  boundary was determined.

# condense-json 1.0 release notes (verbatim), condense-json 1.1 release notes (verbatim)
# Source: https://github.com/simonw/condense-json/releases/tag/1.0
#         https://github.com/simonw/condense-json/releases (1.1 entry)

## 1.0 (released 2026-08-02 22:19 UTC)
- condense_json() now can now round-trip inputs that include the keys $, $r,
  and $raw. These are now escaped using a $raw wrapper. (#3)
- Overlapping replacements are now deterministic: matches are selected from
  left to right, with the longest match winning.
- uncondense_json() now raises UncondenseError, a subclass of ValueError, for
  malformed condensed data, including unknown or blank replacement IDs,
  non-list $r values, and invalid $r segments.
- Type annotations now cover any JSON-compatible top-level value through the
  exported recursive JSONInput alias.

## 1.1 (released 2026-08-03 04:56 UTC — ~6.5 hours after 1.0)
- Replacements object can now include values other than strings. These will
  be identified and used as structural replacements by condense_json() and
  uncondense_json(). (#8)
- Objects can be used as the basis for merge operations. condense_json() will
  identify if there are objects that are a close match and will store
  instructions for keys to update or delete. uncondense_json() can then apply
  these merges. (#8)
- Now includes additional round-trip tests using hypothesis.

## Guide Impact

- **Chapter 04 (Context Engineering)**: The existing token-efficiency
  guidance (informed by `blog-jetbrains-ponytail-token-savings-test.md`
  and `blog-ghaw-weekly-2026-06-22.md`) covers *prompt-input* compression
  (fewer tokens sent to the model). This source adds a distinct, adjacent
  practice: *storage-side* compression of what gets logged *after* a
  model call — specifically, deduplicating a raw provider response against
  data a harness has already normalized elsewhere (Claim 2/6). Recommend
  adding this as a named pattern for teams building conversation/response
  logging: (1) identify caller-supplied or already-normalized content that
  providers echo back verbatim (response text, tool definitions — Claim
  10), (2) replace exact-string recurrences with references rather than
  storing them twice, and (3) reconstruct the replacements mapping at read
  time from already-immutable state rather than storing it (Claim 7), to
  avoid reintroducing the duplication the scheme is meant to remove. Flag
  the caveat from Claim 11: exact-match/substring deduplication schemes
  silently stop working when two logically-identical copies of the same
  content are not byte-identical (e.g., per-event encryption in a
  streaming API) — the fix has to happen upstream of the dedup step, not
  inside it.
- **Chapter 04 (Context Engineering) — measurement discipline**: When
  citing this source's compression numbers (86% / 42-48% / 40% /
  15%->50%), attach the length- and payload-type-dependence noted in
  Claim 8/9/10: these are single-author, live-call measurements on
  specific payload shapes (a 400-word response, a tool-call turn, a
  streamed-reasoning turn), not a general "condense-json saves X%" figure
  that would generalize to arbitrary JSON.
